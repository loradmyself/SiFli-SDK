🔍 为什么连上第二副耳机，第一副就会卡？
当 SF32 仅连接第一副耳机时，系统资源相对充裕，能保证音频流稳定。但当连接第二副耳机时，系统负载发生显著变化，可能从以下几个方面导致 Host 端“断供”：

CPU 负载与调度冲突：SF32 采用双核架构（如高性能核 HCPU + 低功耗核 LCPU）。开启双连接后，HCPU 需要同时处理两路 A2DP 编码、协议栈调度和内存管理，负载骤增。若音频编码任务的优先级被其他任务抢占，就会因来不及处理数据而导致发包延迟。

内存与带宽瓶颈：双 A2DP 流意味着需要维护两个编码器的状态和对应的缓冲区。如果 SRAM 带宽或堆栈空间不足，可能导致内存访问延迟或频繁的垃圾回收，直接阻塞音频数据通路。

协议栈与蓝牙控制器瓶颈：单控制器需同时管理两条 A2DP 链路，增加了协议栈的调度开销。若控制器缓冲区（Credits）不足，Host 就会因流控而暂停发送音频数据，对应抓包中 Credit 相关字段的变化。

SDK 示例的“单连接”限制：SiFli 的 BT A2DP Sharing 官方示例文档明确指出，部分系列（如 sf32lb52-lcd、sf32lb56-lcd）仅支持连接一个耳机做音频转发。你当前的双耳机 Demo 可能是在其基础上修改，或使用了非标准实现，可能存在未被完全优化的并发路径。

🛠️ 针对 SF32 平台的排查与优化建议
你可以按以下顺序，从易到难进行排查和优化：

1. 确认 SDK 与 Demo 的“双连接”支持情况
   首先确认你使用的 SDK 版本和 Demo 是否官方原生支持双耳机音频转发。可以查阅 a2dp_sharing 示例的 README 或 Kconfig，查看是否有相关的双连接使能选项（如 CONFIG_BT_A2DP_MULTI_CONN 等）。如果官方仅支持单连接，双连接下的卡顿可能属于已知限制。
2. 监控系统负载，定位瓶颈
   CPU 利用率：在卡顿复现时，通过调试串口输出或系统监控工具，查看 HCPU 和 LCPU 的实时利用率。重点关注 A2DP 编码任务和蓝牙协议栈任务的 CPU 占用是否接近饱和。

内存使用：检查系统堆（Heap）的剩余空间，以及音频缓冲区的使用水位。双流并发时，确保缓冲区有足够的深度来吸收调度抖动。

任务优先级：确认音频编码和数据发送任务的优先级是否设置得足够高，避免被其他低优先级任务（如 UI 刷新、日志打印）阻塞。

3. 优化任务调度与核心绑定
   鉴于 SF32 的双核架构，可以尝试将关键任务绑定到特定核心，减少核间迁移带来的开销和不确定性：

将音频编码/发送任务绑定到 HCPU（高性能核），确保其有充足的算力。

将蓝牙协议栈任务绑定到 LCPU（低功耗核）或独立的处理核心，避免与音频任务抢占 HCPU 资源。具体绑定方法需参考 SF32 SDK 中关于任务创建和核心亲和性（Core Affinity）的 API。

4. 调整蓝牙与音频流参数
   SBC 编码参数：在保证音质的前提下，可尝试降低 SBC 编码的比特率或复杂度（如调整 subbands、bitpool 等参数），以减轻 CPU 负载。

缓冲区深度：适当增大音频发送缓冲区和蓝牙控制器缓冲区的深度。这不能解决根本的性能问题，但能提供更大的容错空间，平滑短暂的调度延迟。

5. 分析日志与抓包，定位具体延迟点
   串口日志：在卡顿发生时，观察是否有 underflow、buffer full、timeout 等错误打印。这些日志能直接指出是编码器、协议栈还是驱动层出了问题。

HCI 抓包：继续使用 Frontline 分析。除了看 Sequence Number，重点观察 HCI Number Of Completed Packets 事件 和 Host 的 Credits 字段。如果在卡顿期间，Credits 长期为 0 或 Completed Packets 事件停止，则说明瓶颈在控制器或空中接口；如果 Credits 充足但 Host 不发包，则瓶颈在 Host 应用/协议栈层。

💎 总结
问题根源在于双 A2DP 流并发使 SF32 Host 侧的资源（CPU、内存、调度）无法同时满足两路音频流的实时性要求。建议优先从确认 SDK 双连接支持和监控系统负载（CPU/内存） 入手，结合日志和抓包定位到具体的瓶颈资源（是 CPU 算力、内存带宽，还是协议栈调度），再针对性地进行优化。

### 💡 为什么会导致第一副耳机卡顿？

结合你“SF32 芯片，连第一副正常，连第二副时第一副卡顿”的背景，真相大白了：

**这是典型的“蓝牙协议栈资源竞争”导致的 Host 侧阻塞。**

1. **CPU 算力被抢占** ：当第二副耳机接入时，SF32 的蓝牙 Host 层（协议栈）需要处理大量的信令包（SDP 查询、L2CAP 建链、AVDTP 协商、RFCOMM 建链等）。这些信令处理的优先级如果在代码里设置得比“第一副耳机的音频发送任务”高，或者占用了大量 CPU 时间，就会导致音频数据包发不出去。
2. **互斥锁/内存资源竞争** ：蓝牙协议栈通常有全局锁或共享的内存池。在建立新连接时，如果持有锁的时间过长，正在发送第一路 A2DP 音频的线程就会被强制挂起，直到信令处理完毕。
3. **回调函数阻塞** ：连上第二副耳机后，系统可能会触发一些应用层的回调（比如配对成功、连接成功事件），如果这些回调函数里有耗时操作，直接就把音频发送的线程卡死了。

### 🛠️ 怎么解决/优化？

针对 SF32 平台，你可以从以下几个方向入手：

1. **调整任务优先级 (Task Priority)** ：

* **调高 A2DP 发送任务优先级** ：在 RTOS 中，确保负责读取音频数据并往蓝牙控制器塞数据的任务优先级足够高，不被信令处理任务抢占。
* **拆分/降低信令任务优先级** ：如果 SDK 允许，尝试将非紧急的蓝牙信令处理放到低优先级的任务队列中。

1. **检查回调函数** ：排查当第二副耳机连接时，用户代码里注册的连接成功回调函数（Callback）。不要在回调里做 `printf` 打印（很耗时）、内存分配或延时操作。
2. **开启缓冲区/加大水位** ：

* 在 SF32 的音频 pipeline 中，尝试加大发送缓冲区的深度。虽然不能消除这 360ms 的处理延迟，但可以避免耳机端立刻出现卡顿（用缓冲数据顶上）。

1. **优化双 A2DP 流的发送策略** ：

* 不要在连接第二副耳机的瞬间，同步发送两路音频。可以尝试在握手期间，短暂暂停第一路的音频流（发送 A2DP Suspend），等第二路完全连上、系统稳定后，再同时开启两路发送。

1. **核心绑定 (Core Affinity)** ：

* 如果 SF32 是双核（如 HCPU/LCPU），看看能否把蓝牙底层协议栈（Controller 驱动）和音频编码（Host App）绑定到不同的核心上，减少中断和上下文切换的开销。

**下一步建议：**
去翻一下 SF32 的 SDK 代码，找到蓝牙连接状态机（比如 `BT_CONNECTION_STATE` 变化的地方），看看当状态变成“第二副耳机已连接”时，系统执行了哪些应用层代码，大概率就是那里阻塞了音频流。
