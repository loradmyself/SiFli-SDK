SiFli HFP 蓝牙通话 3A/AEC 开发指南

面向 main/example/bt/hfp 例程的实战指南：从建立一通电话开始，讲清 3A 算法的代码位置、mic 与喇叭两路数据的流转路径、把 AEC 参考信号接进自研算法的方法，以及把这两路原始 PCM 数据 dump 出来做离线分析的完整操作。

1. 你将学到什么

本文按“先跑起来、再看清数据流、最后换算法、随时能抓数据”的顺序组织，读完可以独立完成一轮 AEC 调参与验证。

  • 编译、烧录并让 HFP 例程真正进入一通通话的完整步骤
  • 3A（AEC/NS/AGC）代码在 SDK 中的位置，以及编译时到底选中了哪个实现
  • 通话上下行两条数据通路的每一个节点、缓冲区与帧长约定
  • AEC 从哪两个函数、哪两个缓冲区拿到近端与远端数据
  • 把自研 AEC 算法移植进 SDK 的两种方式、接口契约与踩坑清单
  • dump 出 mic 与喇叭两路 PCM 的两种方式、指令参数、文件落盘位置与解析脚本

TL;DR：这个例程默认就跑着 WebRTC 的 AECM + NS + AGC 三件套。喇叭实际播放的数据经 audio_3a_far_put() 进入 WebRtcAecm_BufferFarend() 作为远端参考，mic 采集数据经 audio_3a_uplink() 做降噪后进入 WebRtcAecm_Process() 作为近端，两者在 audio_3a_data_process() 里汇合；换自研算法只需实现同一组接口并改一行 SConscript；抓这两路数据用 audio_data -aecm_input1 -audprc 一条命令即可。

2. 前置要求

在动手之前，先确认软硬件环境齐备，避免卡在工具链或串口上。

项目要求
硬件eh-lb525 或本例程支持的其他板子（见 README 的支持平台列表）
SDKSiFli-SDK，本例程路径 main/example/bt/hfp
工具链scons + 对应 ARM 工具链；SifliTrace（串口 dump 用）
手机支持 HFP 的蓝牙手机，用于建立真实通话
基础了解 RT-Thread 设备模型、环形缓冲（ringbuffer）基本概念
前置知识PCM 音频格式（16 bit / 单声道）、回声消除的基本原理（参考信号 + 近端信号）

3. 例程怎么用

本节从编译烧录讲到用 finsh 命令真正打通一通电话，并确认 3A 已经启动——这是后面所有操作的前提。

3.1 编译与烧录

在 project 目录执行编译命令：

cd main/example/bt/hfp/project
scons --board=eh-lb525 -j32

编译完成后进入生成的 build_eh-lb525 目录，运行下载脚本，按提示输入串口编号即可。烧录完成后复位，串口会打印系统启动日志。

cd build_eh-lb525
./uart_download.bat

3.2 用 finsh 命令建立通话

例程启动后默认已打开蓝牙，全部操作通过 hfp_cmd 命令完成：

步骤命令成功标志
搜索手机hfp_cmd start_inquiry打印 device [xxx] searched 与设备地址
停止搜索hfp_cmd stop_inquiry—
连接手机hfp_cmd hfp_connect xx:xx:xx:xx:xx:xxHFP HF connected
拨打电话hfp_cmd make_call 10086make a call complete
接听来电hfp_cmd answer_callanswer a call complete
建立通话音频hfp_cmd audio_connectHFP HF audio_connected
挂断hfp_cmd handup_callhangup a call complete

注意：只有 audio_connect 成功、SCO 链路建立之后，3A 才会真正启动。没进入通话状态时调用 dump 命令抓不到任何数据，因为 audio_3a_open() 还没被调用、is_need_3a 还是 0。

3.3 确认 3A 已跑起来

通话建立后，串口应能看到 3A 初始化的日志（由 audio_3a_open() 打印）：

3a_w open samplearate=16000
WebRtcNsx Init finish !
WebRtc Aecm Init finish !
WebRtc Agc Init finish !
g_ul_agc_compression_gain_db=18, g_dl_agc_compression_gain_db=10, g_agc_decay=100, g_echoMode=3

看到这几行，说明 NS / AECM / AGC 三个模块都已创建成功，后续 dump 才有意义。若只看到 3a_w open 而没有算法初始化日志，检查是否被 PKG_USING_WEBRTC 相关配置关掉了。

4. 3A 从哪里来：源码选择与配置

目录里同名文件有好几个，先弄清编译期到底选中了谁，再谈改算法。

4.1 编译期选型

middleware/audio/audio_voice_proc/SConscript 用 Kconfig 宏在多个实现之间二选一（互斥，只编一个）：

5. 数据路径全景

一通电话里数据分两条路走，最终在 audio_3a_data_process() 汇合。理解这两条路，是理解后面 AEC 取数和 dump 打点的基础。

5.1 下行（手机 → 喇叭）

手机 HFP/SCO
  → BT 协议栈解码（mSBC / CVSD）
  → audio_bt_voice.c: audio_3a_downlink(fifo, size)
  → rbuf_dwlink 环形缓冲（按帧切分）
  → 下行 AGC
  → speaker_ring_put()
  → audio_server TX 环形缓冲
  → audio_server 取出 tx_data_tmp（叠加音量）
  → audio_3a_far_put(tx_data_tmp, tx_dma_size)
  → rbuf_far 环形缓冲
  → WebRtcAecm_BufferFarend()   ← 远端参考信号
  → 同时 bf0_audprc_device_write() 写到喇叭硬件

关键点在于 audio_3a_far_put() 拿到的不是蓝牙原始下行数据，而是经过下行 AGC、又叠加了用户音量的 tx_data_tmp——也就是真正送到喇叭功放的那份数据。这一点非常重要：AEC 要用“喇叭实际发出什么声音”作为参考，才能抵消麦克风拾取到的回声。

5.2 上行（mic → 手机）

mic 采集（audprc RX，DMA 半满/全满中断）
  → audio_server.c: audio_3a_uplink(rx_data_tmp, 320, is_mute, is_bt_voice)
  → audio_3a_data_process()（每帧 320 字节 @16k）
      ├─ DC 直流校正
      ├─ NS 噪声抑制
      ├─ AECM 回声消除      ← 近端信号在此与远端参考相减
      ├─ 上行 AGC
      └─ RampOut
  → rbuf_out 环形缓冲
  → bt_voice_encode_process() 编码（mSBC / LC3）
  → 回传手机

5.3 帧长与缓冲约定

采样率每帧字节 (frame_len)帧时长每帧样点数说明
8000 Hz16010 ms80窄带通话（CVSD）
16000 Hz32010 ms160宽带通话（mSBC），最常见
32000 Hz3205 ms160超宽带（LC3 SWB）

audio_3a_uplink() 入口处有 RT_ASSERT(fifo_size == 320)，即无论采样率，上层每次固定送 320 字节；8k 情况下内部会拆成两次 160 字节分别处理。三个环形缓冲的用途如下：

缓冲生产者消费者容量
rbuf_faraudio_3a_far_put()（TX 侧）AEC 取参考帧320 B（32k 为 480 B）
rbuf_dwlinkaudio_3a_downlink()（BT 侧）下行 AGC1280 B（32k 为 1920 B）
rbuf_out3A 处理完的上行数据编码器320 B（32k 为 480 B）

6. AEC 怎么拿到两路数据

这是移植和调试时最需要搞清楚的一段：两个入口一近一远，一个在发送喇叭的时机、一个在收到 mic 的时机。

6.1 远端参考：audio_3a_far_put()

调用者是 audio_server.c 的喇叭发送路径（process_speaker_tx()）。每送一帧给喇叭硬件之前调用一次：

/* audio_server.c，写喇叭前 */
if (my->is_need_3a)
{
    audio_3a_far_put(my->tx_data_tmp, my->tx_dma_size);
}
bf0_audprc_device_write(my->audprc_dev, 0, my->tx_data_tmp, my->tx_dma_size);

audio_3a_far_put() 内部只做三件事：入 rbuf_far、按 frame_len 切帧、逐帧喂给算法并打点：

/* audio_3a.c: audio_3a_far_put() */
if (rt_ringbuffer_space_len(p_3a_env->rbuf_far) >= fifo_size)
    rt_ringbuffer_put(p_3a_env->rbuf_far, fifo, fifo_size);

while (rt_ringbuffer_data_len(p_3a_env->rbuf_far) >= p_3a_env->frame_len)
{
    rt_ringbuffer_get(p_3a_env->rbuf_far, (uint8_t *)farframe, p_3a_env->frame_len);
    audio_dump_data(ADUMP_AECM_INPUT1, (uint8_t *)farframe, p_3a_env->frame_len);
    WebRtcAecm_BufferFarend(p_3a_env->aecmInst,
                            (const int16_t *)farframe,
                            p_3a_env->frame_len / 2);
    p_3a_env->is_far_putted = 1;   /* 标志位：远端已有数据，AEC 可以开始工作 */
}

三个要点：接入点是 WebRtcAecm_BufferFarend()，自研算法把这里换成自己的 xxx_Farend() 即可；frame_len / 2 是样点数（字节数除以 2），别传错；is_far_putted 是“远端已就绪”的闸门，AEC 处理分支会先判断它，避免上电初期用空参考去消回声。

6.2 近端：audio_3a_uplink() → audio_3a_data_process()

mic 数据由 audio_server.c 在每次 ADC 数据就绪时送入：

audio_3a_uplink(my->rx_data_tmp, readlen, server->public_is_rx_mute, server->is_bt_3a);

audio_3a_data_process() 是整条链路的骨架，用 SWAP_IN_OUT() 在两个帧缓冲之间来回倒腾，顺序固定为 DC → NS → AECM → AGC → RampOut：

/* 简化后的核心流程 */
memcpy(in, fifo, fifo_size);
audio_dump_data(ADUMP_AUDPRC, fifo, fifo_size);          /* 原始 mic 打点 */

DcCorrection_Process(dcInst, in, out, frame_len / 2);    /* DC 校正 */
audio_ans_proc(pNS_inst, in, out);                       /* NS 降噪 */
audio_dump_data(ADUMP_ANS_OUT, out, frame_len);

if (p_3a_env->is_far_putted && g_u16_test_aec)
{
    aec_input_para_t para = {
        .nearframe = in,          /* 降噪后的 mic：近端 */
        .nearframe_clean = NULL,
        .outframe = out,
    };
    audio_dump_data(ADUMP_AECM_INPUT2, in, frame_len);
    audio_aec_proc(aecmInst, &para, samplerate);         /* 回声消除 */
}
audio_dump_data(ADUMP_AECM_OUT, out, frame_len);

audio_agc_proc(agcInst, in, out, samplerate);            /* 上行 AGC */
RampOut_Process(rampOutInst, in, out, frame_len / 2);
rt_ringbuffer_put(rbuf_out, out, frame_len);

真正调用 WebRTC 的那一层：

/* audio_3a.c: audio_aec_proc() */
int16_t audio_aec_proc(void *aecmInst, aec_input_para_t *para, uint16_t samplerate)
{
    uint16_t u16_frame_len = 80;
    if (16000 <= samplerate) u16_frame_len = 160;

    if (0 != WebRtcAecm_Process(aecmInst,
                                para->nearframe,        /* 近端（含回声） */
                                para->nearframe_clean,  /* 输出回声估计，可为 NULL */
                                para->outframe,         /* 消除后的结果 */
                                u16_frame_len,
                                g_aec_delay))           /* 近远端延时，单位 ms */
    {
        LOG_W("WebRtcAecm_Process  error !\n");
        return 1;
    }
    return 0;
}

6.3 两路数据是怎么对上的

两路来自不同线程、不同时刻，靠下面四个机制保证时序能对上：

机制说明
同节拍产生上下行都由音频 DMA 中断驱动，都是 10 ms 一帧
环形缓冲削峰rbuf_far / rbuf_out 吸收两侧调度抖动
延时补偿g_aec_delay（默认 10）告诉 AEC 参考信号相对近端滞后多少 ms
就绪闸门is_far_putted 保证有参考数据后才开始消回声

调试时如果发现回声消不干净，g_aec_delay 是第一个该动的参数：它对应“从数据写入喇叭到被麦克风拾取”的声学加电路延时，不同腔体、不同喇叭功率差别很大，10 ms 只是通用起点。

7. 移植自己的 AEC 算法

移植的核心不是算法本身，而是契约：帧长、样点数、调用上下文、缓冲管理，四项对不上就会出现断续、延时漂移甚至死机。本章先给两条落地路径，再逐条列坑。

7.1 两种方式

方案 A（推荐）：新增实现文件。新增 audio_3a_myaec.c，实现与 audio_3a.c 相同的一组接口，然后在 SConscript 加一个分支：

# middleware/audio/audio_voice_proc/SConscript
if GetDepend('PKG_USING_3MICS'):
    src = []
elif GetDepend('PKG_USING_MYAEC'):
    src = Glob('audio_3a_myaec.c')
elif GetDepend('PKG_USING_SOUNDPLUS'):
    src = Glob('audio_3a_soundplus.c')
# ... 其余分支保持不变

再在 Kconfig 里加上 PKG_USING_MYAEC 选项，工程 proj.conf 中打开它、同时关掉 CONFIG_PKG_USING_WEBRTC。优点是：不动原文件，后续 SDK 升级不冲突；可随时切回 WebRTC 做 A/B 对比。

方案 B：直接改 audio_3a.c。只替换 audio_aec_proc() 内部实现，其余链路（NS / AGC / dump / 缓冲）全部复用。适合只想换 AEC 内核、保留其它处理的场景。改动量最小，但后续 SDK 升级需要重新合入。

7.2 接口契约

无论哪种方案，都必须实现下面这组函数（声明见 middleware/audio/include/audioproc.h）：

函数调用者调用上下文职责
audio_3a_open(audio_3a_input_t *input)audio_server.c 通话建立时线程按 input 中的 samplerate 初始化算法，申请内存
audio_3a_close(void)通话结束时线程释放全部资源
audio_3a_uplink(uint8_t *fifo, uint16_t len, uint8_t is_mute, uint8_t is_bt_voice)mic 数据就绪音频线程，10 ms 一次处理近端，结果写回 fifo；is_mute 时输出静音
audio_3a_downlink(uint8_t *fifo, uint16_t size)BT 下行解码后BT 语音线程处理下行并 speaker_ring_put() 送喇叭
audio_3a_far_put(uint8_t *fifo, uint16_t size)写喇叭前TX 发送路径接收远端参考，喂给算法
audio_3a_dnlink_buf_is_full(uint16_t size)下行数据到来前BT 语音线程流控，缓冲不够返回 1
audio_3a_set_bypass(uint8_t bypass, uint8_t mic, uint8_t down)产测命令线程直通开关，旁路全部算法
audio_command_process(uint8_t *cmd)调试通道线程参数下发入口，可留空

audio_3a_input_t 结构（新版接口，注意与旧版四参数原型不同）：

typedef struct
{
    uint32_t samplerate;         /* 8000 / 16000 / 32000 */
    uint8_t  is_bt_voice;        /* 1: 蓝牙通话，输出要交给编码器 */
    uint8_t  disable_uplink_agc; /* 1: 关闭上行 AGC */
    uint8_t  all_mic_channels;   /* mic 通道数 */
    uint8_t  enable_mic_ssl;     /* mic 特定处理开关 */
} audio_3a_input_t;

7.3 移植要点与坑

  1. 帧长是硬约束：上层固定送 320 字节；内部按 frame_len（16k 为 320、8k 为 160）切帧。自研算法若不支持 10 ms 帧，需要在内部做缓存重排，不能直接改上游。
  2. 样点数不是字节数：所有算法 API 的长度参数都是 int16 样点数，等于字节数除以 2。
  3. 不要 malloc：audio_3a_uplink() 在音频线程里 10 ms 调用一次，函数内动态内存分配会造成抖动甚至丢帧，全部改在 open() 里预分配。
  4. 上下文与耗时：这段代码跑在音频服务线程，单帧预算 10 ms，WebRTC 定点 AECM 通常只占几百微秒。自研算法若复杂度高，建议开 AUDIO_3A_STATIC_TIME 用 audio_tick_in/out 打点，或把重活搬到 ACPU（参考 WEBRTC_RUN_IN_ACPU 的做法）。
  5. is_far_putted 闸门要保留：否则上电前几十毫秒会用全零参考去消回声，反而把近端语音削掉。
  6. bypass 要能真直通：audio_3a_set_bypass(1, ...) 必须让数据原样透传，产测和问题定位都靠它。
  7. 保持 dump 打点：把 audio_dump_data() 调用照抄进你的实现，否则后面没法用同一套工具抓数据；每个 audio_dump_type_t 只能被一路数据占用。
  8. ringbuffer 满要处理：rbuf_out 满时丢帧会直接体现为上行断续，LOG_I("3a_w rbuf_out full") 是重要线索。
  9. 32k 特例：frame_len 仍是 320，但一帧只有 5 ms，samplerate 分支要单独验证。

7.4 移植后的验证顺序

按下面顺序逐级验证，出问题时能快速定位是哪一层不对：

  1. 先 audio_3a_set_bypass(1, 0, 0) 验证通路（应能正常通话，无算法介入）；
  2. 打开自研算法，dump ADUMP_AECM_INPUT1 与 ADUMP_AECM_INPUT2，确认两路数据都有、帧率一致；
  3. 对比 ADUMP_AECM_OUT，用耳机/扬声器两种模式分别做听感评估；
  4. 最后再调 NS、AGC 的增益与门限。

8. 怎么 dump 出数据

SDK 内置了一套音频 dump 框架，在 3A 链路的每个节点都埋了打点，取数不需要自己写代码。本章给出两种导出方式、完整指令表与落盘路径。

8.1 两种方式怎么选

维度串口方式（默认）文件方式
开关#define AUDIO_DATA_CAPTURE_UART再加 #define AUDIO_DATA_CAPTURE_FILE
输出实时打到 console 串口，由 SifliTrace 接收写入设备文件系统
依赖console 串口 TX DMA + finsh追加依赖 DFS + 可写文件系统（建议 NAND）
优点无需文件系统，边跑边看不受串口带宽限制，可长时间录
缺点带宽受限，dump 期间看不到 log需要导出文件，nor flash 速度可能不够

两个宏都在 middleware/audio/audio_manager/audio_server.c 顶部（约 72 行）：

#define AUDIO_DATA_CAPTURE_UART
//#define AUDIO_DATA_CAPTURE_FILE

注意：切到文件方式时，AUDIO_DATA_CAPTURE_UART 必须保留。整个 audio_data 命令包在 #if defined (AUDIO_DATA_CAPTURE_UART) && defined (RT_USING_FINSH) 里，把它注释掉 finsh 里就没有这个命令，执行时会提示找不到指令。文件方式靠 AUDIO_DATA_CAPTURE_FILE 让 dump 目标从串口切到文件，不需要牺牲命令本身。

8.2 可用指令与参数

audio_data 命令的参数与数据类型一一对应：

参数数据内容对应位置
-audprc原始 mic 采集数据（进算法前）audio_3a_data_process() 入口
-downlink蓝牙下行原始数据（解码后）audio_3a_downlink()
-downlink_agc下行 AGC 后数据（即送喇叭前）audio_3a_downlink() 尾部
-aecm_input1喇叭参考信号（AEC 远端）audio_3a_far_put()
-aecm_input2AEC 前 mic 数据（AEC 近端）AEC 调用前
-aecm_outAEC 消除后的上行数据AEC 调用后
-ans_outNS 降噪后数据NS 之后
-agc_out上行 AGC 后数据AGC 之后
-ramp_out_out最终送 BT 编码的数据RampOut 之后
-dc_outDC 校正后数据DC 之后
-pdmPDM 麦克风原始数据audio_3a_save_pdm()
-stop / -off停止 dump，恢复 log—

常用组合：

# AEC 近端 + 远端参考（做离线 AEC 分析的标准两路）
audio_data -aecm_input1 -audprc

# 看 AEC 前后效果
audio_data -aecm_input1 -aecm_out

# 看喇叭实际播放的数据 + 原始 mic
audio_data -downlink_agc -audprc

# 三路（注意串口带宽）
audio_data -downlink -downlink_agc -aecm_out

8.3 串口方式操作步骤

  1. 确认 CONFIG_BSP_UART1_TX_USING_DMA=y（本工程已开）；关掉 BT HCI log 释放串口带宽，然后重启设备： 
    nvds update hci_log 0
  2. 建立通话（见 3.2 节），确认 3A 已初始化。
  3. 打开 SifliTrace，选择 console 串口并连接，选择音频功能。
  4. 输入 dump 命令，串口会回应 dump enable 与 audio_data_start: enable 2 2848，此时系统 log 暂停（正常现象），数据开始往串口灌： 
    audio_data -aecm_input1 -audprc
  5. 录够时长后停止： 
    audio_data -stop
  6. 在工具里点保存，数据落在 SifliTrace 的 log 目录下 xxx_audio/ 子目录，工具已按类型拆好，得到 xxx_audprc.pcm 与 xxx_aecm_input1.pcm 两个文件。

8.4 串口的数据帧格式

串口上跑的是一条复用流，每帧前面带 12 字节头，工具依据 type 拆包：

typedef struct
{
    uint32_t magic;   /* "AUDI"，小端值 0x49445541 */
    uint16_t type;    /* 见 8.2 参数与枚举的对应关系 */
    uint16_t len;     /* 本帧字节数，16k 时 320 */
    uint32_t no;      /* 该类型自己的帧序号 */
    uint8_t  data[320];
} audio_data_t;       /* 头长 AUDIO_DATA_HEADER_LEN = 12 */

8.5 文件方式操作步骤

文件方式适合长时间录制，代价是依赖设备端文件系统。操作顺序如下：

  1. 修改 audio_server.c 顶部两个宏（两个都要开）： 
    #define AUDIO_DATA_CAPTURE_UART
#define AUDIO_DATA_CAPTURE_FILE
  2. 重新编译烧录。开机 log 确认文件系统已挂载，出现 mount fs on flash to root success 才可用；未见此行说明 BSP_USING_SPI_NAND / RT_USING_DFS 未生效。
  3. 通话中执行同样的命令： 
    audio_data -downlink_agc -audprc
  4. 数据直接落到根目录，每一路一个独立文件，没有 12 字节包头，纯 PCM。
  5. 录制时长由 g_record_time 控制，默认 10 秒（audio_3a.c 中 uint32_t g_record_time = 10;）。max_frame = g_record_time * 1024 / 10，16k 下约 1024 帧、10.24 秒。要录更长直接改这个默认值再编译；当前版本 audio_command_process() 的 time= 解析被 #if 0 屏蔽，运行时改不了。
  6. 到时间自动关闭文件，也可以手动 audio_data -stop 提前结束。手动停止且文件仍打开时，每个文件尾部会追加 12 字节记录 {0x55667788, cur_frame, max_frame}，分析时若长度不是帧长整数倍，先砍掉末尾 12 字节。
  7. 文件导出：ls / 查看，建议用 SifliTrace 的文件读取或 SifliBleApp 的 GET DUMP 拉取。不建议直接 cat——二进制数据经 console 打印既慢又容易和 log 混淆。

各数据类型对应的落盘文件：

数据类型文件路径

喇叭参考（AEC input1）/dump_aecm_input1.pcm
AEC 前 mic（input2）/dump_aecm_input2.pcm
AEC 输出/dump_aecm_out.pcm

8.6 离线解析脚本

串口文件是带头的复用流，用下面脚本拆成多路；文件方式的产物已经是纯 PCM，可跳过：

import struct

raw = open("dump.bin", "rb").read()
out = {0: open("downlink.pcm", "wb"),
       1: open("downlink_agc.pcm", "wb"),
       2: open("audprc.pcm", "wb"),
       5: open("aecm_input1.pcm", "wb"),
       6: open("aecm_input2.pcm", "wb"),
       7: open("aecm_out.pcm", "wb")}
i = 0
while i + 12 <= len(raw):
    magic, typ, ln, no = struct.unpack_from("<IHHI", raw, i)
    if magic != 0x49445541:      # "AUDI"
        i += 1                   # 串口丢字节时重同步
        continue
    i += 12
    if typ in out:
        out[typ].write(raw[i:i + ln])
    i += ln

PCM 参数：16000 Hz（8k 场景为 8000 Hz）、16 bit、单声道、小端。用 Audacity 时选 File → Import → Raw，编码 Signed 16-bit PCM、字节序 Little-endian、声道 Mono。

9. 常见问题 FAQ

问：为什么 audio_3a_dummy.c 里全是空函数？答：它是编译兜底实现，只有在没选任何 3A 包时才会被编入。本工程选了 PKG_USING_WEBRTC，实际编译的是 audio_3a.c。

问：AEC 参考信号为什么不用蓝牙下行原始数据？答：参考必须是“喇叭真正发出的声音”。下行原始数据没经过 AGC 和音量调节，幅度与实际播放不一致，用它做参考会导致自适应滤波器收敛到错误的增益上。

问：audio_3a_uplink() 里为什么要断言 320 字节？答：这是上层音频服务的固定节拍，与采样率无关。8k 时内部拆成两帧 160 字节处理，改动这个约定会破坏整个上下行时序。

问：能否只替换 AEC、保留 NS 和 AGC？答：可以。采用方案 B，仅替换 audio_aec_proc() 内部实现，NS（audio_ans_proc）与 AGC（audio_agc_proc）保持不动即可。

问：dump 出来的两路数据能直接对齐做 AEC 吗？答：能，但要注意两点：两路的帧序号 no 是各自独立计数的，不能直接比较；真正的时间关系由 g_aec_delay 描述，离线处理时先用互相关估一下实际延时再验证。
