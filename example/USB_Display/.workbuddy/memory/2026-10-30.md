# 2026-10-30

## 工程分析（USB_Display / SiFli-SDK）

- 工程定位：SiFli-SDK `main/example/USB_Display`，README 仍是 hello_world 模板，与实际代码无关。
- 实际代码只有 `src/` 三个文件：`main.c`（应用层，轮询取帧 + `draw_rect` 全屏刷新）、
  `usb_display_device.c`（USB 描述符 / 事件 / PSRAM 帧池 / 4 个对外 API）、`usb_config.h`（CherryUSB 裁剪）。
- `driver/` 是 **PC 端 Windows IDD 驱动**（xfz1986，VID 303A / PID 2986），不是嵌入式代码。
- 构建：`project/` SCons，需先跑 SDK 根 `set_env.bat` 设置 `SIFLI_SDK`；当前 shell 中该变量为空。
  现有 Keil 工程目标板 `sf32lb58-lcd_base`，芯片 SF32LB58x，HCPU。

## 发现的缺陷（未修复，已向用户报告）

1. `FRAME_BUF_SIZE = 390*450*2 = 351000` 不是 16384 整数倍，而新版 `usbd_display.c` 有
   `USB_ASSERT_MSG(frame_bufsize % 16384)` 断言 → init 阶段死循环。正确值 `22*16384 = 360448`。
2. 同类根因：驱动每包固定读 16384B，最后一包会越界约 5.3KB（池仅 351000+4096）。
3. `frame_pool[1]` 实际单缓冲，注释却写 double-buffered → 绘制期间丢帧。
4. 未定义 `CONFIG_USB_HS` → MPS 64 全速，带宽上限约 1.2MB/s，带宽需求 5.27MB/s（15fps×351KB）不可能满足。
5. `main.c` 用 20 字节头启发式判断协议版本，但类驱动帧头结构体为 16 字节且 `frame_size = payload_total`，判断可能失效。

## PC 侧驱动（xfz1986 IDD v1.2.0.1）逆向结论 — 对后续开发很关键

- 产品字符串按 `%[^_]_%[^_]_%[^_]` 只解析**前 3 段**，合法格式 `名字_R<w>x<h>_Ergb<16>`；
  DLL 中不存在 `Fps` / `Bl` 字符串 → `_Fps15_Bl128` 后缀无效。
- 编码器只找到 `rgb888x_encoder_rgb565` → **设备侧只能收 RGB565（Ergb16）**，Ergb24 会走 "wrong Enc str" 回退。
- DLL 内硬编码显示器模式表（均 60Hz）：
  240x240 / 280x240 / 320x240 / 480x272 / 480x320 / 480x480 / 640x480 / 800x480 /
  800x600 / 960x960 / 1024x600 / 1024x768 / 1280x600 / 1280x720 / 1280x800 / 1600x1200 / 1920x1080。
- 驱动把 Windows 选中模式**缩放**到产品字符串里的面板分辨率（日志 `scale...%d to %d`、`scale_res`）。
  ⇒ 换分辨率无需改 PC 驱动，但要挑与模式表同分辨率或同宽高比的屏，否则拉伸/黑边。

## 硬件能力（58X = SF32LB586 同家族）

- LCDC 物理接口（docs/source/zh_CN/hal/lcdc.md）：3SPI(1/2线)、4SPI(1/2线)、QAD-SPI、DSI Command、
  DSI Video、DBI 8080-8bit、JDI、DPI、AHB→SRAM/PSRAM 均支持；**不支持** QSPI DDR、DBI-16bit、TCON。
- 输出色格式：RGB332 / RGB565 / RGB888 / RGB565_SWAP。58X 支持**硬件解压缩图层**（可吃 JPEG）。
- 58x 另有独立 JPEG 编解码器（`drivers/hal/bf0_hal_jpegd.c`、`drivers/cmsis/sf32lb58x/jpegdec.h`）。
- 板名规则：`a128r32n1` = 128MB SPI NAND + 32MB PSRAM + 1MB NOR。58x 的 NAND 板为
  `sf32lb58-lcd_a128r32n1_{qspi,dsi,a1_dsi}`，默认屏 CO5300 390x450，且 `CONFIG_PSRAM_CACHE_WB=y`。

## 用户目标

在 **586 NAND** 板（应为 `sf32lb58-lcd_a128r32n1_qspi` 一类）上实现 USB 副屏。
后续若继续开发，优先解决上面 1/2/3/4 四项，并确认 PSRAM 帧缓冲的 cache 一致性（MUSB 驱动有 clean/invalidate）。

## 副屏调试：DPI 局部刷新黑屏问题（已修复）

- 现象：扩展模式下副屏只有最后推送的脏矩形内容（窗口）显示，其余全黑。
- 根因：DPI 屏没有 GRAM，`drv_lcd` 的 `draw_rect` 语义是"整层缓冲替换"——
  ST7265 `LCD_WriteMultiplePixels` → `HAL_LCDC_LayerSetData`（只记指针+区域，无拷贝）→
  LCDC 把紧凑矩形缓冲放到 TL/BR 位置合成，画布其余区域=背景色黑。
  QSPI GRAM 屏才能真"局部画上去"。
- 修复（main.c）：新增持久全屏帧缓冲 `screen_fb`（L2_RET_BSS_SECT，768KB PSRAM），
  每帧按帧头 x/y/w/h 合成进 fb → `SCB_CleanDCache_by_Addr` 清脏区 → 整屏 `draw_rect`。
- 修复（usb_display_device.c）：`FRAME_BUF_SIZE` 768000 → 自动向上取 16384 倍数（770048，
  需容纳 16B 帧头+payload=768016）；`frame_pool[1]`→`[2]` 双缓冲，池 2×770048+4096。
- 结论：PC 驱动协议与 2026 版 CherryUSB display 类驱动的 16 字节帧头匹配（payload_total=768000 精确命中证明）。

## 性能优化文档已输出

- 实测 `lcd_ctrl fps 1` ≈ 24fps；瓶颈 = draw_rect 同步等 DPI 扫描（17-35ms/帧）。
- 优化路线：P1 去掉每帧 draw_rect（图层一次配置，LCDC 自扫）→ P2 EPIC 合成 →
  P3 JPEG 链路（Ejpg80 + JPEGD 硬解，60fps 正解）→ P4 fb 迁 HCPU SRAM + 结构重构。
- RGB565 全帧方案 USB 天花板 ≈ 45-50fps；60fps 必须走 JPEG。
- 多核结论：HCPU 调度 + EPIC/JPEGD/LCDC 三 DMA 引擎并行；LCPU 跑 BLE、ACPU 音频，不搬任务。
- 文档：example/USB_Display/OPTIMIZATION_PLAN.md（含已修复问题备忘、PC 驱动侧已知事实、验收标准）。

  应用 800x480 与 LCDC 1024x600 不匹配 → DPI_HW_FSM_START 断言（bf0_hal_lcdc_aux.c:128，

  bytes_per_line/2=HAW, repeat_count×2×SRAM_BUF_LINES=VAH。

  usbd_display.c 帧边界改用编译期真实总线 MPS（USBD_DISPLAY_BUS_MPS，FS=64/HS=512）。
  该假设尚未在 57 上最终验证。
- 58 上一切正常（HS + 描述符512 + 边界512 等价原逻辑）。P1 优化已生效：
  main.c 每帧 draw_rect 已注释，仅启动时推一次整屏，LCDC 自扫 screen_fb。
  副作用：lcd_ctrl fps 不再有输出（统计挂在 draw_core 内），已改用主循环每秒打印
  "USB fps=N, total=M"（main.c）。
- menuconfig 结论：SiFli SDK 构建时 ResolveBoardConfig 每次从 board.conf+proj.conf
  重新生成 .config；menuconfig 保存是"最小diff且排除board.conf符号"，choice 类切换
  不可靠，proj.conf 必须手写为唯一事实来源。
